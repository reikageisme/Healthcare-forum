## Implementation

| Task | Current implementation |
| --- | --- |
| T2.1 — token kinds | `src/core/security.ts` requires the expected token kind at verification. `src/middleware/auth.ts` requests `access`; `src/routes/auth.ts` requests `refresh`. Missing, unknown and non-string kinds are rejected. Roles still come from the database. |
| T2.2 — UUID subject | The shared verifier validates `sub` with `asUuid` before either user lookup. Missing/malformed subjects fail with 401 on required auth and behave anonymously on optional auth. Expiry is now mandatory and validated without coercion. |
| T2.3 — inactive accounts | Existing login, refresh and required-auth checks are retained and tested. Inactive login/refresh return 403 without tokens; required auth returns 403; optional auth becomes anonymous. |
| T2.4 — auth regressions | `backend/tests/auth.test.ts` adds 52 tests and passes both in isolation and in the complete backend suite, including existing admin RBAC coverage. |

New tokens contain `iat` and a random UUID `jti`. Previously, issuance depended
only on subject, role, type and expiry, so a login followed by refreshes within
one second returned identical tokens. Unique IDs make each new pair distinct
while preserving the configured access and refresh lifetimes.

Source analysis found two production callers of `decodeToken`: the shared
user loader and the refresh handler. Both now pass their expected kind. The
existing standalone `asUuid` behavior used by other routes is unchanged.

## Session cutover and remaining boundaries

The implementation requires explicit token types at both boundaries. On
deployment, legacy untyped sessions will need a fresh login; there is no
compatibility window. Existing correctly typed, unexpired sessions continue
without requiring `iat` or `jti`. This makes the strict G2 behavior concrete
for review; it does not record production-rollout approval or close the
broader POLICY-01 gate.

Refresh remains stateless. An earlier typed refresh token remains usable
until expiry while its account is active; `jti` uniqueness does not revoke
that token or provide reuse detection. Server-side revocation and single-use
refresh storage were not part of the G2 tasks.
